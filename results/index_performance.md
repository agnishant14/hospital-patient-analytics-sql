# Index performance benchmark

`analysis/09_index_performance.sql` compares eight workloads with the four nonclustered indexes in `schema/06_create_indexes.sql` against the clustered primary key alone.

## Status

The harness has not yet been run on a real SQL Server instance. No performance numbers are claimed. Current analytical exports were generated by the Python oracle, which cannot provide SQL Server reads or timings.

## Method

- Warm each workload twice.
- Measure it seven times per index configuration.
- Use logical 8 KB page reads as the primary metric.
- Report minimum elapsed time to reduce scheduler-noise effects.
- Discard runs with unstable logical reads.
- Include a point-lookup control and a full-table aggregate control.

## Pre-run expectations

| Workload | Expected outcome |
| --- | --- |
| 1–4 | Moderate read reduction from narrower covering-index scans |
| 5 | Little improvement because the doctor index does not include `WaitTimeMinutes` |
| 6 | Little improvement because no index starts with `PaymentMethodID` |
| 7 | Point lookup should fall to single-digit reads |
| 8 | Full-table aggregate should remain nearly unchanged |

The fact table is small enough to fit in memory, so elapsed-time gains may be minor. The most actionable result would be workload 5 confirming that `WaitTimeMinutes` should be added to the doctor index. Any added index must still justify its storage and write-amplification cost.
